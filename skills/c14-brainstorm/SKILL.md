# 轻量 Brainstorm

把模糊想法收敛为经用户确认的设计结论。这个 Skill 只负责讨论和决策，不负责产出工程制品。

## 边界

- 不修改文件、代码、配置或外部状态。
- 不自动生成 PRD、spec、计划或任务清单文件。
- 不提交代码，也不自动转入实现、TDD 或其他 Skill。
- 设计确认后停止；可以建议下一步，但等待用户另行授权。

## 工作流

### 1. 建立上下文

先复述目标和当前已知约束。若问题依赖现有仓库，先只读检查相关代码、文档与历史，避免向用户询问可以直接查明的事实。

区分三类信息：

- 已确认事实
- 暂定假设
- 需要用户决策的问题

### 2. 沿决策依赖逐题澄清

每轮只问一个问题。先解决会影响后续选择的上游决策，再讨论实现细节。

提问时：

- 优先给出 2–3 个互斥选项，并标注推荐项及简短理由。
- 选项无法覆盖问题时，再使用开放式问题。
- 不为完整而追问无关细节；能安全假设的内容应明确写出假设并继续。
- 主动确认目标用户、成功标准、关键约束、非目标及主要失败场景。

### 3. 比较可行方案

当存在实质性取舍时，给出 2–3 个方案。先讲推荐方案，再说明各方案在复杂度、维护成本、兼容性、风险和可逆性上的差异。

不要为了凑数制造伪方案。若只有一个合理路径，直接说明原因并验证用户是否接受。

### 4. 分段确认设计

按问题规模分段呈现设计，每段只覆盖一个可独立判断的主题，例如：

- 用户流程或系统边界
- 核心组件与职责
- 数据流、状态与接口
- 异常处理和边界条件
- 验证方式与验收标准

每段后询问是否准确；若用户否定，先修正该段，再继续下一个主题。

### 5. 收敛并停止

获得确认后，输出一份聊天内的简洁结论，包含：

- 目标与约束
- 选定方案及理由
- 关键决策
- 边界条件与失败处理
- 验收标准
- 明确不做的事项
- 尚未解决的问题（如有）
- 建议的下一步

不要把总结写入文件，也不要执行建议的下一步。

## 对话原则

- 以帮助用户做决定为目标，而不是展示分析过程。
- 控制每轮信息量；复杂主题拆小，但不要把简单问题仪式化。
- 对重要取舍给出明确观点，不用含糊的“都可以”。
- 新信息推翻旧假设时，明确指出变化，并同步修订已确认的结论。
